# [PROJECT_NAME] SDD Constitution

Spec-Driven Development (SDD) constitution, adapted from [GitHub Spec-Kit](https://github.com/github/spec-kit) (CC0/MIT) for **DeepSeek Harness (DSH)**. This constitution is the architectural DNA for this project: every specification, plan, and task generated through the SDD skills must comply. It is tuned to DSH's execution model — filesystem-discovered skills plus runtime subagents.

## How SDD runs on DeepSeek Harness

SDD is delivered to this project as DSH skills installed under `.dsh/skills/` (`sdd-specify`, `sdd-plan`, `sdd-tasks`, `sdd-constitution`, `sdd-analyze`, `sdd-clarify`, `sdd-converge`, `sdd-implement`, `sdd-checklist`). Each skill is a `SKILL.md` the agent loads mid-conversation. Long-running or parallelizable work is delegated to DSH subagents (`research`, `task`, `consistency`). Specifications live under `specs/<NNN-slug>/`; this constitution lives at `memory/constitution.md`.

## Core Principles

### I. Specification-First
Every feature starts as `specs/<NNN-slug>/spec.md` generated by the `sdd-specify` skill — WHAT users need and WHY, never HOW. No implementation or plan exists before its spec. The spec is the source of truth; code is a regenerable expression of it.

### II. Spec-as-Executable Contract
Specifications are precise, complete, and unambiguous enough to generate a working implementation and its tests. Every technical choice in `plan.md` traces back to a requirement in `spec.md`. If a detail is unclear, mark it `[NEEDS CLARIFICATION: ...]` rather than guessing.

### III. Research-Driven, Subagent-Grounded (NON-NEGOTIABLE)
Research and validation are delegated to DSH subagents, not improvised inline:
- `sdd-plan` MUST spawn the **research subagent** to produce `research.md` (library compatibility, performance, security).
- `sdd-implement` MUST spawn **task subagents** to execute `tasks.md` entries (test-first).
- `sdd-analyze` MUST spawn the **consistency subagent** to check the spec for ambiguity, contradiction, and gaps against this constitution.

### IV. Continuous Consistency Validation
Consistency is not a one-time gate. On every plan/task (re)generation, run `sdd-analyze` against spec, plan, tasks, and this constitution. Resolve all contradictions before proceeding.

### V. Integration-First Testing
Tests use realistic environments: prefer real databases/services over mocks and stubs; contract tests are written before implementation. Test scenarios are part of the specification that generates both implementation and verification.

### VI. Simplicity & Anti-Abstraction Gates
`plan.md` must pass the Phase -1 gates before tasks are generated:
- **Simplicity**: ≤3 projects for the initial implementation; no future-proofing; no speculative "might-need" features.
- **Anti-Abstraction**: use the framework directly; a single model representation; no wrappers unless justified in "Complexity Tracking".
Any intentional breach is documented with rationale in Complexity Tracking.

## Development Workflow

1. `sdd-guardian` — at intake of any new tool/task/capability, verify constitutional coverage; amend BEFORE implementing anything not yet governed.
2. `sdd-specify` — feature description → `spec.md` + branch `<NNN>-<slug>`.
3. `sdd-clarify` — resolve `[NEEDS CLARIFICATION]` markers.
4. `sdd-plan` — spec → `plan.md`, `data-model.md`, `contracts/`, `quickstart.md`; spawn research subagent.
5. `sdd-tasks` — plan → `tasks.md` with `[P]` parallel markers.
6. `sdd-analyze` — constitution compliance + consistency check.
7. `sdd-implement` — execute tasks (test-first) via task subagents.

All PRs and reviews must verify compliance with this constitution.

## Governance

This constitution supersedes other practices. Amendments require documented rationale, maintainer approval, a backwards-compatibility assessment, and a migration plan for in-flight specs.
